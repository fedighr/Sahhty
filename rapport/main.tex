\chapter{Tests and Validation}

\section{Introduction}

This chapter presents the validation process conducted to evaluate the reliability, security, and functional correctness of the Sahhty platform. Given the healthcare-oriented nature of the application and the sensitivity of pregnancy-related data, special attention was given to validating both the functional behavior of the system and the consistency of its decision-making logic.

The testing strategy combines five complementary phases: \textbf{unit and automated testing}, which verifies isolated backend logic and critical business rules, \textbf{integration testing}, which validates the interaction between system components and external services, \textbf{functional testing}, which ensures that each feature behaves correctly according to defined requirements, \textbf{security testing}, which enforces access control and protection against common attack patterns, and \textbf{performance testing}, which evaluates system responsiveness under concurrent usage conditions.

The following sections describe the adopted testing methodology, the testing environment and tools used, as well as the different test scenarios and the obtained results.

\section{Testing Strategy and Methodology}

The development of the Sahhty platform followed an Agile Scrum methodology, where testing activities were integrated throughout the development lifecycle. To ensure structured validation and traceability between requirements and test cases, the adopted testing strategy follows the \textbf{V-Model} approach.

The Sahhty platform is built on a layered architecture composed of a REST API layer, a business logic service layer, and a real-time communication layer using WebSockets for critical events. In addition, external notification channels (FCM and email) are used to ensure reliable delivery of asynchronous alerts. This architecture required a testing strategy that ensures validation at multiple levels: isolated business logic validation, API-level functional correctness, and cross-channel consistency between real-time and offline communication systems.

This methodology associates each development phase with a corresponding validation phase, allowing progressive verification of the implemented functionalities. The validation process was organized into multiple complementary phases, including automated and unit testing, functional testing, integration testing, security testing, and performance testing, as illustrated in Figure \ref{fig:vmodel}.

\subsection{Software Environment}

The Sahhty platform was developed and tested using a full-stack environment composed of a Django backend and a Flutter frontend. The backend was executed locally using the development server at \texttt{127.0.0.1}, while the database was hosted on Neon PostgreSQL.

\begin{itemize}
    \item \textbf{Backend:} Django 6.0.2 with Django REST Framework 3.16.1
    \item \textbf{Programming Language:} Python 3.13.5
    \item \textbf{Database:} Neon PostgreSQL (cloud-hosted relational database)
    \item \textbf{Frontend:} Flutter 3.3+ with Riverpod state management
    \item \textbf{Mobile Testing:} Android emulator and real Android device (realme 12x 5G)
    \item \textbf{Server Environment:} Localhost development server (127.0.0.1)
    \item \textbf{Testing Structure:} Modular Django architecture with a dedicated \texttt{tests.py} file in each application
\end{itemize}

The real-time communication system was implemented using Django Channels, enabling asynchronous WebSocket communication between the server and clients for instant event delivery.

\subsection{External Services}

The platform integrates multiple external services to support its functionality:

\begin{itemize}
    \item \textbf{Firebase Cloud Messaging (FCM):} Used for push notifications when the application is in background or closed.
    \item \textbf{Brevo Email Service:} Used for transactional email delivery including OTP verification and system notifications.
    \item \textbf{OTP System:} Custom implementation using Python's \texttt{secrets} module with time-based expiration handling.
    \item \textbf{Groq API (LLaMA 3.3 70B):} Used during data preprocessing and medication normalization, particularly for cleaning and standardizing drug-related entries.
\end{itemize}

\section{Security Testing}
% =====================================================================

\subsection{Objective}

Security testing aims to verify the robustness of the Sahhty platform's authentication system, the protection of sensitive medical data, and the enforcement of role-based access control. The objective is to ensure that unauthorized users cannot access protected resources and that the system resists common attack patterns.

\subsection{Strategy}

Security tests were performed by simulating various unauthorized access scenarios, token manipulation attempts, and boundary condition attacks targeting the authentication and permission enforcement layers of the REST API.

\subsection{Test Cases}

\subsubsection{Test Case SEC-001 — Unauthenticated Access to Protected Endpoint}

\begin{itemize}
    \item \textbf{Priority:} Critical
    \item \textbf{Precondition:} No JWT token provided in the request headers.
    \item \textbf{Steps:} Send a GET request to \texttt{/patients/PatientService/} without an Authorization header.
    \item \textbf{Expected Result:} HTTP 401 Unauthorized is returned.
    \item \textbf{Actual Result:} \textbf{\textcolor{green}{PASSED}} — server correctly rejects the request with HTTP 401.
\end{itemize}

\subsubsection{Test Case SEC-002 — Manipulated JWT Token}

\begin{itemize}
    \item \textbf{Priority:} Critical
    \item \textbf{Precondition:} A valid JWT token with a manually modified payload.
    \item \textbf{Steps:} Modify the JWT payload to escalate the role to \texttt{admin} and send a request to a protected endpoint.
    \item \textbf{Expected Result:} HTTP 401 or 403 returned — signature validation fails.
    \item \textbf{Actual Result:} \textbf{\textcolor{green}{PASSED}} — invalid signature detected, access denied.
\end{itemize}

\subsubsection{Test Case SEC-003 — Cross-User Data Access (Horizontal Privilege Escalation)}

\begin{itemize}
    \item \textbf{Priority:} Critical
    \item \textbf{Precondition:} Authenticated as Patient A.
    \item \textbf{Steps:} Attempt to access Patient B's medical files by providing Patient B's ID in the URL.
    \item \textbf{Expected Result:} HTTP 403 Forbidden returned.
    \item \textbf{Actual Result:} \textbf{\textcolor{green}{PASSED}} — ownership check enforced, access denied.
\end{itemize}

\subsubsection{Test Case SEC-004 — Doctor Accessing Unauthorized Patient Data}

\begin{itemize}
    \item \textbf{Priority:} Critical
    \item \textbf{Precondition:} Authenticated as a Doctor without access authorization from the patient.
    \item \textbf{Steps:} Attempt to retrieve the medical file of a patient who has not granted access.
    \item \textbf{Expected Result:} HTTP 403 Forbidden returned.
    \item \textbf{Actual Result:} \textbf{\textcolor{green}{PASSED}} — permission check enforced correctly.
\end{itemize}

\subsubsection{Test Case SEC-005 — Expired JWT Token}

\begin{itemize}
    \item \textbf{Priority:} High
    \item \textbf{Precondition:} A JWT token whose expiration date has passed.
    \item \textbf{Steps:} Use the expired token to call a protected endpoint.
    \item \textbf{Expected Result:} HTTP 401 Unauthorized returned.
    \item \textbf{Actual Result:} \textbf{\textcolor{green}{PASSED}} — expired tokens are correctly rejected.
\end{itemize}

\subsubsection{Test Case SEC-006 — Brute Force Protection on Login}

\begin{itemize}
    \item \textbf{Priority:} High
    \item \textbf{Precondition:} Active login endpoint.
    \item \textbf{Steps:} Submit more than 5 incorrect login attempts consecutively for the same account.
    \item \textbf{Expected Result:} Account temporarily blocked or response delay introduced.
    \item \textbf{Actual Result:} \textbf{\textcolor{orange}{PARTIAL}} — repeated failed attempts return HTTP 400 consistently; a formal rate-limiting mechanism is planned for a future iteration.
\end{itemize}

\section{Performance Testing}
% =====================================================================

\subsection{Objective}

Performance testing aims to evaluate the behavior and stability of the Sahhty platform under concurrent usage conditions. The goal is to determine the system's capacity to handle simultaneous requests while maintaining acceptable response times and error rates.

\subsection{Testing Configuration}

Performance tests were conducted using \textbf{Locust 2.x} targeting the most critical API endpoints of the platform. The tests simulated progressive user load to identify performance thresholds and degradation points.

\begin{itemize}
    \item \textbf{Tool:} Locust 2.x (Python-based load testing framework)
    \item \textbf{Target Endpoints:} \texttt{POST /users/auth/signin/}, \texttt{GET /patients/PatientService/}, \texttt{GET /measurements/MeasurementService/}, \texttt{GET /appointments/AppointmentService/}
    \item \textbf{Authentication:} Valid JWT token injected per virtual user
    \item \textbf{Ramp-up:} 5 users per second
    \item \textbf{Test Iterations:} 20, 50, 100, 200, 500 concurrent users
\end{itemize}

\subsection{Load Test Results}

\begin{table}[H]

\subsection{Analysis}

The results reveal three distinct behavioral zones:

\begin{itemize}
    \item \textbf{Stable zone (20–100 users):} The platform maintains response times below 350 ms with a near-zero error rate, confirming reliable performance under normal expected usage conditions for a medical mobile application.
    \item \textbf{Degradation zone (200 users):} Response times increase significantly (620 ms average) with an error rate of 1.8\%, indicating the system begins to approach its capacity limit.
    \item \textbf{Critical zone (500 users):} At 500 concurrent users, the system experiences significant latency exceeding 2 seconds and an error rate above 8\%, suggesting the need for horizontal scaling or caching strategies for production deployment.
\end{itemize}

\textbf{Recommendations:}
\begin{itemize}
    \item Introduce query-level caching for frequently accessed read endpoints (medication list, appointment list).
    \item Enable database connection pooling using \texttt{django-db-connection-pool}.
    \item Deploy behind a load balancer with multiple backend instances for production-scale usage.
    \item Activate response pagination on all list endpoints to reduce data transfer per request.
\end{itemize}

The Sahhty platform demonstrates stable performance for up to 100 concurrent users with acceptable response times, which is consistent with the expected usage scope of a medical mobile application serving a regional patient base. \section{Summary and Recommendations}
% =====================================================================

\subsection{Key Strengths}

\begin{itemize}
    \item \textbf{Core functionalities validated:} Authentication, appointment management, treatment processing, AI risk assessment, and alert generation all operate correctly across all tested scenarios.
    \item \textbf{Security enforced:} JWT-based access control, role-based permissions, and ownership checks are reliably applied across all protected endpoints.
    \item \textbf{Integration consistency:} All system modules (authentication, medical services, notification pipeline, AI engine) communicate correctly and maintain data consistency throughout the operation.
    \item \textbf{AI risk assessment functional:} The XGBoost-based pregnancy risk model is correctly triggered upon measurement submission and returns structured risk levels.
    \item \textbf{Multi-channel notifications reliable:} FCM push notifications, email delivery via Brevo, and WebSocket real-time alerts are all confirmed to operate correctly in integration.
    \item \textbf{Stable performance under expected load:} The system maintains response times under 350 ms for up to 100 concurrent users, which is consistent with the target deployment scale.
\end{itemize}

\subsection{Recommendations and Future Improvements}

\begin{itemize}
    \item \textbf{Implement rate limiting} on the authentication endpoint to protect against brute force attacks using Django's throttling middleware.
    \item \textbf{Introduce caching} on frequently read endpoints (medication list, patient profile) using Redis to improve response times under higher load conditions.
    \item \textbf{Expand automated test coverage} to include appointment lifecycle scenarios, notification channel validation, and AI model edge cases.
    \item \textbf{Deploy behind a reverse proxy} (e.g., Nginx) with multiple Gunicorn workers for production-ready scaling.
    \item \textbf{Activate JWT token refresh} mechanism to avoid forcing users to re-login after token expiration.
\end{itemize}
